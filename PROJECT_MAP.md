# PROJECT_MAP.md — карта проекта для ИИ-ассистентов

Этот файл — вход в проект для Claude/Cursor/Cline и любого другого ИИ, который будет здесь
дорабатывать код. Прочитай его целиком перед первым изменением. Он объясняет не только
«что где лежит», но и **почему** оно так устроено — это экономит на порядок больше времени,
чем чтение самого кода.

См. также [`.cursorrules`](./.cursorrules) — жёсткие архитектурные правила, которые нельзя
нарушать (лейаут, стиль, экономия контекста).

---

## 1. Суть проекта

Веб-инструмент для мастера D&D 5e / любой НРИ. Одна кампания = одна запись в Supabase
(`campaigns`), внутри — вся «вторая память» ГМа: карта мира, NPC, враги, локации, квесты,
лут, фракции, бестиарий, трекер боя, календарь/погода, генерация текста через LLM.

Однопользовательский инструмент (один ГМ ведёт свои кампании), без совместного
редактирования в реальном времени.

## 2. Стек и почему именно так

| Технология | Роль |
|---|---|
| Next.js 16 App Router + Turbopack | Клиентское SPA-приложение поверх Next; серверная часть — только `/api/ai` и авторизация Supabase |
| React 19 | Всё состояние — на клиенте, серверных компонентов с данными почти нет |
| TypeScript (строгий) | Модель сущностей местами типизирована слабо (`Record<string, any>`) — см. раздел 7 |
| Tailwind CSS 4 | Единственный источник стилей. Кастомных `.css`, кроме `globals.css`, нет и не должно быть |
| Zustand + `persist` | Всё состояние кампании — в одном сторе, разбитом на слайсы; персист в `localStorage` |
| Supabase | Auth + таблица `campaigns` (создание/список/автосохранение) + Storage (`maps`, фоны узлов карты) |
| reactflow | Инфинити-канвас мировой карты (`MapBoard`) |
| @dnd-kit | Перетаскивание карточек сущностей в сайдбаре |

## 4. Модель состояния — самое важное

Всё живёт в одном Zustand-сторе `useWorkspaceStore` (см. `store/useWorkspaceStore.ts`),
собранном из 5 слайсов. Это settings, весь мир и все сущности разом.

### 4.1 Библиотека сущностей (`createLibrarySlice`)

12 категорий (`LibraryCategory` в `types/workspace.ts`), каждая — `Record<string, T>`:

`heroes, enemies, quests, locations, loot, events, factions,
characters, extras, bestiary, interactive, secrets`

Для добавления/изменения/удаления **любой** сущности любой категории есть общие экшены —
не пиши категорию-специфичный код без необходимости:

```ts
addEntity(category, entity)      // entity должен иметь entity.id
updateEntity(category, id, data) // мёрджит data поверх текущей записи
deleteEntity(category, id)       // также чистит связанные узлы карты для 'locations'
```

✅ **Миграция npcs→characters / crowd→extras завершена** (было в разделе 7 как известная
проблема). `characters` — теперь единственная каноническая категория для именных
персонажей: объединяет старые `npcs` (игромеханика: hp/ac/goal/secret/isMerchant) и
`characters` (traits/ideals/bonds/flaws/schedule/locationId), плюс новый флаг
`isImportant` для отличия ключевых NPC от второстепенных. `extras` — каноническая
категория для массовки (бывший `crowd`). Формы `NpcForm.tsx`/`CrowdForm.tsx` удалены;
используй `CharacterForm.tsx`/`ExtraForm.tsx`.

Старые кампании (сохранённые в Supabase/localStorage до этой миграции) могут ещё
содержать данные под ключами `npcs`/`crowd` — стор их больше не читает и не пишет, но
данные не теряются, пока ГМ явно не нажмёт «Мигрировать данные кампании» в шапке
(`CockpitHeader.tsx`, кнопка появляется только если `useCampaignSync` обнаружил
несмигрированные данные). Автоматической/молчаливой миграции нет и не должно быть —
см. `utils/migrateLegacyLibrary.ts` и `migrateLegacyData()` в `createLibrarySlice.ts`.

⚠️ **Отдельная, не связанная с этим путаница в `aiTemplateGenerator.ts`**: раздел JSON-схемы
`"extras"` в промпте исторически описывал интерактивные объекты тактической карты
(checks/POI), а НЕ категорию `extras`(массовка) — это была самостоятельная коллизия имён,
из-за которой `importAIData` мёрджил ответ ИИ не в ту категорию. Исправлено: схема
переименована в `"interactive"`, категория `extras` в промпте теперь однозначно описывает
массовку.

### 4.2 Карта (`createMapSlice`)

- `nodes`/`edges` — reactflow-граф мировой карты. Узел с `data.entityId` ссылается на
  запись в `locations`.
- `localMaps: Record<locationId, LocalMapData>` — тактические (боевые) карты внутри
  локации, с сеткой и токенами (`BattleToken`). **Фон тактической карты (`backgroundImage`,
  base64) хранится в IndexedDB** (см. `hooks/useMapBackground.ts`, подробности — раздел 4.3),
  а НЕ в Zustand/localStorage — так и должно быть, это намеренная оптимизация, не баг. Именно
  поэтому `partialize` (в `useWorkspaceStore.ts`) и `useCampaignSync` перед сохранением
  подставляют туда `null`.
- `placeLocationOnMap(locationId, position?)` — кладёт существующую сущность-локацию на
  канвас в виде узла. Общий экшен, используется из `MapBoard` (клик и drag-n-drop, см.
  ниже), из карточки локации в инспекторе (без `position` — на дефолтную позицию), и из
  drag-n-drop моста. Если `position` не передан — падает на дефолт `{x:100, y:100}`.

**Drag-n-drop мост `@dnd-kit` ↔ `reactflow` (`MapBoard.tsx`)**: панель «Локации из Архива»
теперь поддерживает и клик (быстрое добавление на дефолтную позицию), и настоящий drag
мышью на нужное место канваса. Технически: `MapBoard` разделён на `MapBoard` (обёртка с
`ReactFlowProvider`) и `MapBoardInner` (сам компонент) — это обязательно, чтобы
`useReactFlow()` (и его `screenToFlowPosition`) был доступен внутри `MapBoardInner`, а не в
компоненте, который сам рендерит `<ReactFlowProvider>`. Карточки локаций — `useDraggable` из
dnd-kit; во время драга видимую "тень" рисует `DragOverlay` (сама карточка в сайдбаре просто
гаснет до 30% непрозрачности, не двигается). В `onDragEnd` координаты курсора
восстанавливаются как `activatorEvent.clientX/Y + delta` (dnd-kit не даёт готовую текущую
точку курсора) и переводятся в координаты reactflow через `screenToFlowPosition`. Если бросили
за пределами канваса — узел не создаётся.

**Мемоизация `MapNode`** — точечная, не виртуализация (осознанно, см. договорённость по
Блоку 2): `memo(MapNode, areMapNodePropsEqual)` со своим компаратором, который сравнивает
только `id/title/label/mapImage/entityId`. reactflow на каждый кадр перетаскивания/выделения
меняет `xPos/yPos/selected/dragging` в пропсах — но визуал этого компонента от них не
зависит (позиционирование делает сама reactflow через transform обёртки), поэтому дефолтный
неглубокий `memo()` реагировал бы на них зря. Если в будущем понадобится сотни/тысячи узлов
одновременно на экране — тогда, и только тогда, обсуждать полноценную виртуализацию
(windowing), не раньше.

**Blur-up/skeleton для фонов узлов** (`useImagePreload` в `MapNode.tsx`) — фон локации
прелоадится через `new Image()` в фоне; пока не подтверждён `onload`/`.complete`, поверх
рисуется анимированный skeleton-шиммер (`.animate-shimmer`, keyframes в `globals.css`,
единственное место кроме `globals.css`, где разрешён кастомный CSS), а сама картинка держится
`blur-lg`/`scale-110`/`opacity-0` и по загрузке плавно (700ms) переходит в чёткое/нормальное
состояние. Устраняет "моргание" при первом появлении узла на экране.

### 4.3 Тактические карты и бой (`LocalMapBoard.tsx`, `useMapBackground.ts`, `createCombatSlice`)

**Фон боевой карты — приоритет и хранение (Блок 3, п.1).** `useMapBackground(locationId)`
(`src/hooks/useMapBackground.ts`) — единственный источник правды, реализует:
1. Кастомный фон, загруженный ГМом именно для этой боевой карты — живёт **только** в
   IndexedDB (`GMAssistant_Maps` / `backgrounds`), никогда не в Zustand-сторе.
2. Если кастомного фона нет — автофон: `location.mapImage` (лёгкий Supabase Storage URL
   из карточки Архива, Блок 1/2) рендерится сам, без единого действия ГМа.
3. Иначе — пусто.

КРИТИЧЕСКОЕ ПРАВИЛО соблюдено буквально: base64-байты никогда не попадают в Zustand
(ни временно, ни постоянно) — раньше (до Блока 3) `updateMapBackground` клал base64 прямо
в стор, что и партиalize/`buildCampaignSnapshot` подчищали перед записью, но само поле
`localMaps[id].backgroundImage` в живом сторе всё равно временно держало тяжёлые байты.
Теперь это в принципе невозможно — `updateMapBackground` удалён, поле
`LocalMapData.backgroundImage` помечено `@deprecated` и не используется. Который
локейшн реально стоит за конкретной боевой картой — считает `resolveTargetLocationId()`
(экспортирована из `LocalMapBoard.tsx`): проверяет ручную привязку `linkedLocationId` →
`entityId` узла на карте мира → сам `activeLocalMapId`.

**Снеппинг токенов (Блок 3, п.2).** `clientToGridCoords` в `LocalMapBoard.tsx` конвертирует
клиентские координаты в координаты сетки через `Math.round` (не `Math.floor`, как было раньше
— `floor` "прилипал" к клетке сверху-слева, а не к ближайшей). `Math.round` даёт ровно
"прилипание к ближайшей клетке с зоной допуска в полклетки" без явного порога. Во время
перетаскивания сам токен свободно следует за курсором (нативный drag-image браузера), а
`onDragOver` дополнительно подсвечивает клетку, к которой токен прилипнет, если отпустить его
прямо сейчас (`dragPreviewCell` — визуальный аналог зоны допуска, обновляется вживую).
Размер клетки настраивается слайдером (`<input type="range">`) в `MapToolbar`, синхронизирован
с числовым полем — можно подогнать сетку под нарисованный на фоне планшет.

**Модель боя (`createCombatSlice`, `types/workspace.ts::Combatant`).** Нашли и починили
реальный баг при подготовке Блока 3: `Combatant['type']` был `'hero'|'npc'|'monster'` —
`'monster'` никогда не производился `spawnEntityToMap`, а `'enemies'`/`'extra'` (токены
противников и массовки) в список вообще не входили → `startCombat` молча выкидывал их из
боя. Исправлено: `Combatant['type']` теперь `'hero'|'npc'|'enemies'|'extra'`, `startCombat`
подхватывает все четыре. Добавлены `ac: number` и `statuses: string[]` (свободные
текстовые теги состояний — сознательно не хардкодим конкретную редакцию правил). Новые
экшены: `updateCombatantStats(tokenId, {hp?, maxHp?, ac?})`, `addCombatantStatus`,
`removeCombatantStatus`.

**UI трекера (Блок 3, п.4).** `BattleTrackerWidget.tsx` — новая **плавающая** панель поверх
`LocalMapBoard` (перетаскивается за шапку, сворачивается), с полным редактированием
HP/AC/инициативы и тегами статусов. Сознательно НЕ заменяет старый `InitiativeTracker` в
`CockpitSidebar` — тот остался как есть (только починен: раньше он тоже не резолвил
enemies/extra сущности и не показывал их AC/имя).

⚠️ **Ретроактивная зачистка**: удалён `CombatTracker.tsx` — отдельный, полностью
несвязанный со стором мок-трекер (свой локальный React-стейт, собственная 10×10 сетка, не
использовал ни `createCombatSlice`, ни реальные токены боевой карты), который открывался
модалкой с тулбара карты **мира** (`MapBoard.tsx`) — что архитектурно странно, бой должен
происходить на тактической карте. Кнопка его вызова была вообще недостижима (`isCombatOpen`
никогда не переключался в `true`) — то есть это был мёртвый код уже на момент находки. Удалено
по прямому запросу владельца продукта, а не по умолчанию.

### 4.4 UI-система (`createUISlice`) — Блок 4: отмена правила "один экран"

⚠️ **Правило "рендерится строго один экран" из `.cursorrules` ОТМЕНЕНО явным решением
владельца продукта в Блоке 4.** Если увидишь это правило в `.cursorrules` или в старых
комментариях — оно устарело, не следуй ему. Текущая архитектура:

- `activeView` — теперь это **вкладка верхнего уровня**, не "единственный видимый экран":
  `dashboard | archive | map | story | calendar | weather`. Рендерится по-прежнему одна
  вкладка за раз в `hub/[id]/page.tsx` — но каждая вкладка сама вправе показывать
  несколько сосуществующих плавающих панелей поверх себя (см. ниже). Дефолт теперь
  `'dashboard'`, а не `'map'`.
  - `dashboard` → `MasterDashboard.tsx` — Мастер-вкладка (Блок 4, п.2): карта (мировая или
    тактическая — что сейчас открыто, полноценно интерактивная) + плавающие
    `CalendarWidget`/`WeatherWidget` поверх неё одновременно. Виджет боя
    (`BattleTrackerWidget`, Блок 3) уже смонтирован внутри `LocalMapBoard` и появляется
    сам, когда открыта тактическая карта — отдельно монтировать не нужно.
  - `archive` → `ArchiveBoard.tsx` — полноэкранный браузер ВСЕХ категорий сущностей сразу
    (герои, персонажи, массовка, враги, бестиарий, локации, квесты, лут, события,
    фракции), с поиском и созданием записей. Заменил старую узкую вкладку "Герои"
    (`HeroesBoard.tsx` удалён — полностью поглощён этой вкладкой; дефолты нового героя
    типа `hp/ac/level` перенесены в `utils/createBlankEntity.ts`, которым теперь пользуется
    и `CockpitSidebar`, и `ArchiveBoard`, — раньше эта функция была приватной копией внутри
    `CockpitSidebar.tsx`).
  - `map` → `MapBoard`/`LocalMapBoard` в чистом виде, без виджетов календаря/погоды —
    для внимательной работы с картой без отвлекающих панелей.
  - `story` / `calendar` / `weather` → полноразмерные `StoryBoard`/`CalendarBoard`/`WeatherBoard`
    как раньше.
  - `CockpitSidebar` (узкая левая колонка с drag-n-drop на карту) остаётся как есть на всех
    вкладках — это отдельный сценарий (быстрый доступ + перетаскивание), не дублирует Архив.
- `viewedEntityId` — какая сущность открыта в `InspectorPanel` справа.
- `displayMode: 'gm' | 'player'` (Блок 4, п.4) — глобальный переключатель в `CockpitHeader`.
  `'player'` оборачивает весь `InspectorPanel` (все формы `archive/*Form.tsx` разом, без
  правок в каждой по отдельности) в `<fieldset disabled>` — блокирует все нативные
  input/textarea/select/button одним разом. `RichTextEditor` (см. ниже) не подчиняется
  нативному `disabled` fieldset (contentEditable — не форма-элемент), поэтому проверяет
  `displayMode` сам через стор. Это **личная настройка браузера ГМа**, не данные
  кампании — не сбрасывается в `switchWorld`, персистится в `localStorage` отдельно.
- `savedWorlds` / `activeWorldId` / `switchWorld(id)` — **чисто локальный** механизм
  мультимировости внутри одного браузера. `id` совпадает с id кампании в Supabase, но сам
  механизм ничего не знает про облако — это исторически более старая, локальная система
  хранения. Синхронизацию с Supabase поверх неё делает `useCampaignSync` (см. ниже).

**Rich Text Editor + @mention (Блок 4, п.5).** `components/ui/RichTextEditor.tsx` —
Tiptap (`StarterKit` + `Mention` + `Placeholder`), без `tippy.js`: всплывающий список
автокомплита позиционируется вручную через `clientRect()` из Tiptap. Кандидаты на
упоминание — `hooks/useMentionableEntities.ts`, единый источник по ВСЕМ категориям
(герои/персонажи/массовка/враги/бестиарий/локации/квесты/фракции; `secrets` сознательно
исключены — решение Блока 1). Это расширение старой системы из `StoryBoard.tsx`
(`SmartContent`), которая раньше парсила `@Имя` регуляркой уже ПОСЛЕ того, как ГМ дописал
текст, без автокомплита — теперь настоящая подсказка по мере набора текста, с реальными
mention-узлами вместо текстовых совпадений.
- Внедрён в: `StoryBoard.tsx` (главы сюжета, заменяет `SmartContent` целиком),
  `CharacterForm.tsx` (поле "Заметки ГМа"), `LocationForm.tsx` (поле "Описание

**Sonner вместо confirm()/alert() (Блок 4, п.6).** `utils/confirmToast.ts` — замена

### 4.5 Критические фиксы и Блок 5 (время/миры)

- **`app/hub/[id]/page.tsx`**: в Next.js 16 `params` в клиентских компонентах — Promise,
  прямой `params.id` кидает ошибку. Распаковывается через `const { id } = use(params)`
  (React `use()`, не путать с хуком `useEffect`).
- **`InspectorPanel`** теперь настраиваемой ширины (драг-ресайзер за левый край, дефолт
  768px — ровно 2× от старых 384px). Ширина — `inspectorPanelWidth` в `createUISlice`,
  персонажная настройка браузера ГМа (как `displayMode`), не данные кампании.
- **Универсальная картинка сущности** (`EntityImageUploader.tsx`, `utils/uploadEntityImage.ts`)
  — одна точка в `InspectorPanel`, работает для ЛЮБОЙ категории. Пишет в `entity.image`
  для всех категорий, кроме `locations` — там переиспользуется существующее `mapImage`
  (та же картинка, что уже показывает мировая карта и автофон тактической — умышленно не
  плодим для локаций второе, параллельное поле картинки).
- **`WeatherBanner.tsx`** — чисто описательное напоминание по погоде (без хардкода
  игромеханики), показывается и на тактической карте (`LocalMapBoard`), и на мировой
  (`MasterDashboard`, но не одновременно с тактической — иначе задвоение).
- **Индикатор открытого мира** (`CockpitHeader.tsx`) — кликабельный: принудительно пушит
  текущее локальное состояние в Supabase ПРЯМО СЕЙЧАС (`forceSync` в `useCampaignSync.ts`,
  извлечён из общей `performSave`, используется и debounce-автосохранением, и этим ручным
  вызовом). Это push локального состояния в облако, а не pull из облака — сознательно, чтобы
  клик не мог тихо затереть несохранённые локальные правки версией из облака.
- **Переименование кампании** — тут же, по иконке карандаша рядом с индикатором.
  `campaignName`/`renameCampaign` — тоже из `useCampaignSync.ts` (лёгкий отдельный запрос
  `campaigns.name`, отдельно от тяжёлого `map_data`; подгружается при каждом визите, а не
  только при первой загрузке, иначе на повторных заходах индикатор был бы пуст).

## 5. Персистентность — три независимых уровня, не путать

1. **localStorage** (`zustand/persist`, ключ `gm-assistant:workspace`) — быстрый локальный
   кэш всего состояния, работает офлайн. Настраивается в `partialize` в
   `useWorkspaceStore.ts`.
2. **IndexedDB** (`GMAssistant_Maps`) — тяжёлые base64-фоны тактических карт (раздел 4.2).
3. **Supabase, таблица `campaigns`, колонка `map_data` (JSONB)** — облачная копия для доступа
   с другого устройства. Реализована в `hooks/useCampaignSync.ts`:
   - при первом открытии кампании на устройстве, если локального слепка ещё нет —
     подтягивает `map_data` из облака и гидрирует стор;
   - дальше — **дебаунс-автосохранение** (2 секунды простоя) при любом реальном изменении
     данных кампании (сравнивает JSON, чтобы не писать в Supabase на пустом месте);
   - **это last-write-wins**, без конфликт-резолюшена и без realtime — двух ГМов,
     редактирующих одну кампанию одновременно из разных вкладок, не поддерживает. Если
     понадобится реальное совместное редактирование — нужен Supabase Realtime и
     дизайн конфликтов заново, это НЕ мелкая доработка текущей системы.
   - статус синхронизации (`loading|idle|saving|saved|error`) показывается пилюлей в
     `CockpitHeader`.

Фоны узлов *мировой* карты (`MapNode.tsx`, не тактических) — это отдельный, третий случай:
загружаются в Supabase Storage (`bucket: maps`) и в состоянии/облаке хранится только
маленькая публичная ссылка, не base64. Так и должно быть — не переделывай на IndexedDB.

## 6. `/api/ai` — единственный серверный роут

- Требует авторизованную Supabase-сессию (проверяется через `utils/supabase/server.ts`).
  Без неё — 401. Это специально: раньше роут был открыт всем и бесплатно жёг серверный
  `OPENROUTER_API_KEY` — не убирай эту проверку без замены на другой anti-abuse механизм.
- Провайдер (`gemini` | `openrouter`) валидируется по вайтлисту, `model` — по regex
  (защита от инъекции в URL).
- Клиент может передать свой `apiKey` (BYOK, хранится в `useSettingsStore`, персистится в
  `localStorage` в открытом виде — осознанный компромисс, см. `README.md`); если не передал —
  используется серверный `OPENROUTER_API_KEY` как fallback. UI для провайдера/модели/ключа
  и предупреждение о хранении в открытом виде — `SettingsModal.tsx` (раньше эти поля в UI
  ВООБЩЕ ОТСУТСТВОВАЛИ, хотя стор их уже поддерживал — это была скрытая недоделка).
- `utils/aiClient.ts` — единственная точка, откуда стоит дёргать этот роут с клиента
  (`generateAiText`, `enhanceText`).
- **"Умный" контекст (`buildSmartAiContext` в `aiTemplateGenerator.ts`)** — `AiWand.tsx`
  прогоняет `contextData` через эту функцию перед отправкой, вместо `JSON.stringify`
  сырого объекта целиком. Allowlist полей завязан на `mode` (`character`/`location`/
  `loot`/`quest`), дефолт `'general'` просто отсекает тяжёлые ключи
  (`schedule`/`assortment`/`tokens`/...) и обрезает длинные строки. ⚠️ Раньше дефолтным
  `mode` у `AiWand` был `'character'` — это означало, что формы, которые не указывали
  `mode` явно (Enemy/Bestiary/Faction/Extra/Hero/Quest), незаметно получали
  character-специфичную логику тона. Дефолт сменён на безопасный `'general'`;
  `CharacterForm.tsx` теперь указывает `mode="character"` явно.
- **Атмосфера/сеттинг мира — НЕ хардкод, а свойство конкретной кампании.** Раньше здесь
  (и в `route.ts`, и в `generateAIPromptTemplate()`) был жёстко зашитый в код жанр и
  референс на конкретный фильм — это было ошибкой и убрано по прямому решению владельца
  продукта. Правильная схема:
  - `worldSystemPrompt: string` — новое поле в `createSystemSlice` (`SystemSlice`). Это
    свойство МИРА: часть `getEmptyWorldState()`, сохраняется в JSONB-снапшоте Supabase и в
    localStorage вместе с остальными данными кампании — НЕ путать с
    `useSettingsStore.systemPrompt` (личный тон ГМа в конкретном браузере, не путешествует
    между устройствами и не часть кампании).
  - UI — `SettingsModal.tsx`, отдельная секция "Атмосфера и правила генерации мира",
    явно подписанная как свойство кампании, а не браузера.
  - Подмешивается клиентом (`buildCombinedSystemPrompt` в `utils/aiClient.ts`) к
    `systemPrompt` ПЕРЕД отправкой в `/api/ai` — сам роут ничего не знает про атмосферу
    мира и не должен, это исключительно клиентская логика сборки промпта.
  - Для отдельного пути `generateAIPromptTemplate()` (скачиваемый `.txt`-шаблон, не
    проходит через `/api/ai` вообще — см. `DataSyncModal.tsx`) — тот же
    `worldSystemPrompt` передаётся вторым параметром функции и вставляется в текст шаблона
    напрямую.
  - Если `worldSystemPrompt` пустой (дефолт для новой кампании) — никакой жанр или
    сеттинг никуда не добавляется, генератор нейтрален (базовый D&D 5e). Хардкодить
    что-либо на этом месте в коде снова — не надо, это осознанное решение, а не недосмотр.

## 8. Чек-лист перед тем, как вносить изменения

1. Прочитай `.cursorrules` — лейаут и стиль менять нельзя.
2. Новая сущность/категория? Используй `addEntity`/`updateEntity`/`deleteEntity`, не пиши
   свой редьюсер.
3. Меняешь состав полей, которые должны попадать в облако? Обнови
   `buildCampaignSnapshot` в `hooks/useCampaignSync.ts` — иначе новое поле не будет
   переживать переход на другое устройство.
4. Добавляешь тяжёлые бинарные данные (картинки)? Не клади их в Zustand/JSONB — используй
   Supabase Storage (см. `MapNode.tsx`) или IndexedDB для чисто локального кэша (см.
   `LocalMapBoard.tsx`), в зависимости от того, нужна ли синхронизация между устройствами.
5. Трогаешь `/api/ai`? Не убирай проверку авторизации и вайтлист модели/провайдера.
6. После изменений прогони: `npx tsc --noEmit`, `node node_modules/eslint/bin/eslint.js .`,
   `npm run build` (при наличии сети).
